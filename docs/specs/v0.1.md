# Accord v0.1 Specification

## Objective

Provide durable, non-expiring human decision cards for consequential Hermes Agent tool calls. A model turn must not wait for the decision. The owner can later approve, deny, comment, or cancel. All four decisions resume the exact originating stored session with a nonempty hidden decision prompt that includes any optional owner reason. Denial and cancellation never authorize or execute the effect. The plugin enforces any approval against one exact replay of the captured call.

## Current behavior

Hermes `pre_tool_call` hooks can block a call or route it into the native approval prompt. Native approvals belong to a live tool call and have a configured timeout. They are not a durable work queue.

Hermes Desktop persists sessions and exposes `session.resume` and `prompt.submit`. `prompt.submit` supports `display_kind: "hidden"`, which lets the plugin resume an agent without rendering an artificial user bubble.

## Design principles

1. Durable decisions are state, not paused callbacks.
2. Exact authority is a one-use receipt, not a sentence in chat.
3. Comment means revise, not approve.
4. Deny and cancel mean no authority and no effect execution; both still resume the origin with the decision.
5. Unknown or broken state fails closed.
6. Hook-only interception is compatibility mode. Hard enforcement lives in an owned or wrapped effect tool.
7. The agent never approves its own request.

## Scope

### In scope

- Profile-scoped SQLite approval store.
- Explicit policy registry keyed by exact Hermes tool names and optional argument predicates.
- Canonical JSON digest of tool name, profile, effect kind, and complete arguments.
- Adapter-controlled display projection, replay projection, and redaction.
- Persistent Desktop inbox and cards with bounded decision and receipt audit history.
- Owner-authenticated policy settings with bounded, schema-derived tool and field options.
- Approve, deny, comment, cancel, and status operations.
- Exact-origin session continuation after approve, comment, deny, and cancel decisions.
- Exact replay matching and one-use claim.
- `post_tool_call` or execution-wrapper completion receipts.
- Crash recovery from `claimed` to `uncertain`.
- Deterministic demo effect and mock publisher.
- X publication adapter as the first provider integration, disabled until explicitly configured.

### Out of scope for v0.1

- Automatic approval.
- Session-wide or permanent approval.
- Approval based only on natural-language chat text.
- Arbitrary shell parsing as a security guarantee.
- Mobile or remote approval identity.
- Multi-owner quorum approval.
- Scheduling after approval.
- Live X posting in automated tests.
- Claims that the plugin can stop a local user, root process, disabled plugin, or alternate credential path.

## Roles

- **Agent:** requests an effect and receives a durable pending result.
- **Owner:** approves, denies, comments, or cancels through Hermes Desktop.
- **Gate:** persists requests, validates decisions, and authorizes one exact replay.
- **Effect adapter:** selects display fields, redacts sensitive values, validates the call, and optionally verifies the provider result.
- **Hermes Desktop:** renders state and resumes the originating session.

## Proposed flow

### Initial call

1. The agent calls a configured consequential tool.
2. The gate canonicalizes the complete call and computes its digest.
3. The adapter creates a bounded display projection and optional safe replay projection.
4. In one SQLite transaction, the gate reuses an equivalent pending request or creates a new one.
5. The tool does not execute.
6. Hermes receives a structured pending result and the model ends the turn.

### Approve

1. The owner clicks **Approve and continue** on the exact card.
2. The backend records the owner decision against the request digest.
3. Desktop opens or resumes the originating stored session.
4. Desktop submits a hidden continuation naming the approval request and instructing the agent to retry the exact call.
5. On replay, the hook finds one approved request whose profile, session lineage, tool name, and digest match.
6. Execution middleware atomically changes `approved` to `claimed` before dispatch.
7. The tool executes once.
8. The owned effect handler consumes the thread-bound in-process claim before dispatch, so re-entrant calls and copied contexts cannot reuse it.
9. Middleware revokes every context copy when the execution scope returns. An owned handler that returns without consuming its claim fails closed.
10. The completion observer records `executed`, `failed`, or `uncertain` and stores a bounded receipt. Any unclassified exception after claim is `uncertain`; an adapter may report `failed` only with an explicit definitive-failure signal that proves dispatch did not begin.

### Deny

1. The owner clicks **Deny** and may add a reason.
2. The request becomes `denied`.
3. Desktop resumes the exact originating stored session with a nonempty hidden denial prompt, including the optional reason when present.
4. The denial grants no replay authority and cannot execute the original effect.
5. A later identical call creates a new request unless policy suppresses repeated denied calls.

### Comment

1. The owner enters a comment and clicks **Request changes**.
2. The request becomes `changes_requested` and the comment is stored in its audit history.
3. Desktop resumes the exact originating session with a nonempty hidden decision prompt containing the exact comment.
4. No execution authority is granted.
5. Any revised tool call creates a new request and card.

### Cancel

1. The owner clicks **Cancel request** on a pending or change request, or **Revoke approval** on an approved but unclaimed request, and may add a reason.
2. The request becomes `cancelled`.
3. Desktop resumes the exact originating stored session with a nonempty hidden cancellation prompt, including the optional reason when present.
4. No execution authority is granted and the effect is not executed.
5. Cancellation and claim race in one SQLite transaction. The first state transition wins, so the owner cannot revoke a call after execution has claimed it.

### Resume failure

Before Desktop wakes a session, it rejects an empty decision prompt and atomically changes `resume_state` from `pending` or `failed` to `dispatching`. Cancellation cannot win while a resume is dispatching. If Desktop cannot select or retain the target profile, it has not called `session.resume`, so it records `resume_state: failed` and exposes **Retry resume**. Desktop acknowledges delivery only after `prompt.submit` accepts the nonempty hidden prompt. Once Desktop calls `session.resume`, any error is ambiguous: the request remains `dispatching` because the session wake or prompt submission may have succeeded before the response was lost. The gate never retries that uncertain delivery automatically. A caller may record `resume_state: failed` only when it has authoritative proof that delivery did not begin. Approval is not lost and no effect executes out of band.

## State model

Request states:

- `pending`
- `approved`
- `changes_requested`
- `denied`
- `cancelled`
- `claimed`
- `executed`
- `failed`
- `uncertain`

Resume states:

- `not_requested`
- `pending`
- `dispatching`
- `delivered`
- `failed`

Allowed request transitions:

```text
pending -> approved | changes_requested | denied | cancelled
approved -> claimed | cancelled
claimed -> executed | failed | uncertain
changes_requested -> cancelled
```

A changed call never mutates the old request. It creates a new request linked by `supersedes_request_id`. A generic timeout, connection error, or provider exception after claim cannot prove failure and therefore becomes `uncertain`. Adapters must use the narrow definitive-failure exception only when they can prove the effect did not dispatch.

## Canonical authority envelope

```json
{
  "schema": "hermes.human-gate.call.v1",
  "profile": "default",
  "session_lineage": "stored-session-id",
  "tool_name": "provider_create_post",
  "effect_kind": "publish",
  "arguments": {}
}
```

The complete canonical envelope is hashed with SHA-256. The database stores the digest plus adapter-approved projections. An adapter may opt into encrypted or plain safe replay fields. The default stores no unrestricted raw arguments.

## Enforcement levels

### Level 1: interception

A `pre_tool_call` hook blocks configured third-party tools and creates cards. This supports existing tools but depends on the plugin remaining loaded and healthy.

### Level 2: execution claim

A `tool_execution` middleware wrapper claims approved receipts immediately before dispatch and records completion. It prevents two ordinary agent calls from consuming the same approval.

### Level 3: owned effect tool

A tool implemented by or explicitly integrated with Accord performs the gate check inside its handler. If the gate is unavailable, the tool cannot execute. This is the v0.1 security target for publishing.

Raw provider write tools and credential-bearing alternate paths must be disabled for Level 3 to mean anything.

### Owned mock publication envelope

`human_gate_mock_publish` is the network-free Level 3 proof. Its canonical call includes `destination: "mock"`, bounded text, up to four lowercase media SHA-256 digests, an opaque idempotency key, and a deterministic outcome fixture. The approval digest covers every field. The card does not persist the opaque idempotency key, but any change to it still requires a new approval.

The mock provider persists only the SHA-256 digest of the idempotency key, the canonical publication payload digest, a synthetic provider id, and a timestamp. Concurrent calls with the same key and payload converge on one row. Reusing the key for another payload fails. The `uncertain` fixture records the provider result before simulating a lost response; a later newly approved exact retry returns that first result rather than creating another publication. It never contacts X or any other provider.

## Data model

### `requests`

- `id`
- `schema_version`
- `profile`
- `session_id`
- `session_lineage`
- `tool_name`
- `effect_kind`
- `call_digest`
- `display_json`
- `replay_json`
- `state`
- `resume_state`
- `supersedes_request_id`
- `created_at`
- `updated_at`
- `claimed_at`
- `completed_at`

### `decisions`

- `id`
- `request_id`
- `decision`
- `actor_kind`
- `actor_id`
- `comment`
- `created_at`

### `receipts`

- `id`
- `request_id`
- `outcome`
- `result_digest`
- `display_json`
- `created_at`

Receipt audit responses expose only the outcome, result digest, and timestamp. They never return `display_json` because old or third-party receipt writers may not have applied a reviewed display projection. Generic executor failures persist and return only the exception type plus a fixed message, never the provider exception text.

## Stop gates

- Do not connect a live X credential until the mock flow and exact replay tests pass.
- Do not claim arbitrary third-party tools are hard-gated until Hermes supports fail-closed plugin exceptions or the tool integrates the gate inside its own handler.
- Do not publish a release until plugin doctor, unit tests, Desktop tests, and an independent security review pass.
