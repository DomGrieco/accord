# Hermes Human Gate v0.1 Specification

## Objective

Provide durable, non-expiring human decision cards for consequential Hermes Agent tool calls. A model turn must not wait for the decision. The owner can later approve, deny, or comment. Approval and comment resume the originating stored session. Denial closes the request without waking the agent. The plugin enforces any approval against one exact replay of the captured call.

## Current behavior

Hermes `pre_tool_call` hooks can block a call or route it into the native approval prompt. Native approvals belong to a live tool call and have a configured timeout. They are not a durable work queue.

Hermes Desktop persists sessions and exposes `session.resume` and `prompt.submit`. `prompt.submit` supports `display_kind: "hidden"`, which lets the plugin resume an agent without rendering an artificial user bubble.

## Design principles

1. Durable decisions are state, not paused callbacks.
2. Exact authority is a one-use receipt, not a sentence in chat.
3. Comment means revise, not approve.
4. Deny means stop, not retry.
5. Unknown or broken state fails closed.
6. Hook-only interception is compatibility mode. Hard enforcement lives in an owned or wrapped effect tool.
7. The agent never approves its own request.

## Scope

### In scope

- Profile-scoped SQLite approval store.
- Explicit policy registry keyed by exact Hermes tool names and optional argument predicates.
- Canonical JSON digest of tool name, profile, effect kind, and complete arguments.
- Adapter-controlled display projection, replay projection, and redaction.
- Persistent Desktop inbox and cards.
- Approve, deny, comment, cancel, and status operations.
- Same-session continuation after approve and comment decisions.
- Exact replay matching and one-use claim.
- `post_tool_call` or execution-wrapper completion receipts.
- Crash recovery from `claimed` to `uncertain`.
- Deterministic demo effect and mock publisher.
- X publication adapter as the first provider integration, disabled until explicitly configured.

### Out of scope for v0.1

- Automatic approval.
- Session-wide or permanent approval.
- Approval based only on natural-language chat text.
- Arbitrary shell parsing as a security guarantee.
- Mobile or remote approval identity.
- Multi-owner quorum approval.
- Scheduling after approval.
- Live X posting in automated tests.
- Claims that the plugin can stop a local user, root process, disabled plugin, or alternate credential path.

## Roles

- **Agent:** requests an effect and receives a durable pending result.
- **Owner:** approves, denies, comments, or cancels through Hermes Desktop.
- **Gate:** persists requests, validates decisions, and authorizes one exact replay.
- **Effect adapter:** selects display fields, redacts sensitive values, validates the call, and optionally verifies the provider result.
- **Hermes Desktop:** renders state and resumes the originating session.

## Proposed flow

### Initial call

1. The agent calls a configured consequential tool.
2. The gate canonicalizes the complete call and computes its digest.
3. The adapter creates a bounded display projection and optional safe replay projection.
4. In one SQLite transaction, the gate reuses an equivalent pending request or creates a new one.
5. The tool does not execute.
6. Hermes receives a structured pending result and the model ends the turn.

### Approve

1. The owner clicks **Approve and continue** on the exact card.
2. The backend records the owner decision against the request digest.
3. Desktop opens or resumes the originating stored session.
4. Desktop submits a hidden continuation naming the approval request and instructing the agent to retry the exact call.
5. On replay, the hook finds one approved request whose profile, session lineage, tool name, and digest match.
6. Execution middleware atomically changes `approved` to `claimed` before dispatch.
7. The tool executes once.
8. The completion observer records `executed`, `failed`, or `uncertain` and stores a bounded receipt.

### Deny

1. The owner clicks **Deny** and may add a reason.
2. The request becomes `denied`.
3. Desktop does not wake the originating session.
4. The original call cannot execute from that request. A later identical call creates a new request unless policy suppresses repeated denied calls.

### Comment

1. The owner enters a comment and clicks **Request changes**.
2. The request becomes `changes_requested` and the comment is stored in its audit history.
3. Desktop resumes the originating session with the exact comment.
4. No execution authority is granted.
5. Any revised tool call creates a new request and card.

### Resume failure

If Desktop cannot resume the session, the decision remains durable with `resume_state: failed`. The card exposes **Retry resume**. Approval is not lost and no effect executes out of band.

## State model

Request states:

- `pending`
- `approved`
- `changes_requested`
- `denied`
- `cancelled`
- `claimed`
- `executed`
- `failed`
- `uncertain`

Resume states:

- `not_requested`
- `pending`
- `delivered`
- `failed`

Allowed request transitions:

```text
pending -> approved | changes_requested | denied | cancelled
approved -> claimed | cancelled
claimed -> executed | failed | uncertain
changes_requested -> cancelled
```

A changed call never mutates the old request. It creates a new request linked by `supersedes_request_id`.

## Canonical authority envelope

```json
{
  "schema": "hermes.human-gate.call.v1",
  "profile": "default",
  "session_lineage": "stored-session-id",
  "tool_name": "provider_create_post",
  "effect_kind": "publish",
  "arguments": {}
}
```

The complete canonical envelope is hashed with SHA-256. The database stores the digest plus adapter-approved projections. An adapter may opt into encrypted or plain safe replay fields. The default stores no unrestricted raw arguments.

## Enforcement levels

### Level 1: interception

A `pre_tool_call` hook blocks configured third-party tools and creates cards. This supports existing tools but depends on the plugin remaining loaded and healthy.

### Level 2: execution claim

A `tool_execution` middleware wrapper claims approved receipts immediately before dispatch and records completion. It prevents two ordinary agent calls from consuming the same approval.

### Level 3: owned effect tool

A tool implemented by or explicitly integrated with Human Gate performs the gate check inside its handler. If the gate is unavailable, the tool cannot execute. This is the v0.1 security target for publishing.

Raw provider write tools and credential-bearing alternate paths must be disabled for Level 3 to mean anything.

## Success criteria

| ID | Criterion | Evidence |
| --- | --- | --- |
| SC-01 | A pending request survives process and Desktop restart without expiring. | SQLite restart integration test and Desktop reload test |
| SC-02 | Approval authorizes one exact call digest once. | Concurrent claim tests |
| SC-03 | Any argument, tool, profile, or session-lineage change cannot use the approval. | Parameterized mismatch tests |
| SC-04 | Deny cannot reach the effect executor. | Integration test with execution spy |
| SC-05 | Comment cannot reach the effect executor and resumes the session with the exact comment. | API and Desktop test |
| SC-06 | Approve resumes the originating session with a hidden prompt. | Gateway contract test and Desktop test |
| SC-07 | Resume failure leaves the decision durable and retryable. | Failure injection test |
| SC-08 | A crash after claim recovers to `uncertain` and never retries automatically. | Restart recovery test |
| SC-09 | The default adapter persists no unrestricted raw arguments. | Persistence inspection test |
| SC-10 | A disabled or unavailable owned effect gate cannot execute. | Fail-closed handler test |
| SC-11 | Duplicate clicks and duplicate agent retries do not duplicate the effect. | Concurrency and idempotency tests |
| SC-12 | No default test contacts a live provider. | Network-deny test configuration |

## Stop gates

- Do not connect a live X credential until the mock flow and exact replay tests pass.
- Do not claim arbitrary third-party tools are hard-gated until Hermes supports fail-closed plugin exceptions or the tool integrates the gate inside its own handler.
- Do not publish a release until plugin doctor, unit tests, Desktop tests, and an independent security review pass.
